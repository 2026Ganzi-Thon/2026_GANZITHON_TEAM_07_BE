# 문서 기반 개발 절차

## 1. 작업의 근거 찾기

기능 계획·구현, 동작 수정, 프로젝트 초기 구성 전에 이 문서를 읽습니다.
먼저 `docs/service-overview.md`와 `docs/features.md`를 읽고, 요청을 기능 ID와
연결합니다. 초기 구성처럼 기능 ID가 없는 작업은 기반 작업임을 명시합니다.
관련 이슈가 있으면 `docs/agents/issue-tracker.md`에 따라 본문과 댓글을 읽습니다.

현재 사용자 요청으로 작업 범위를 정하고, 아래 문서에서 요구사항과 기존 계약을
확인합니다. 코드·테스트에서는 실제 동작을 확인합니다. 요청·문서·구현이 충돌하면
차이를 알리고 이번 변경에서 따를 동작을 정합니다. 단순한 문서 누락은 확인된
코드 동작을 기록하고, 의도된 동작이 불명확할 때만 필요한 질문을 합니다.

| 작업 영역 | 추가로 읽을 문서 | 확인할 내용 |
| :--- | :--- | :--- |
| API 추가·변경 | `docs/api.md` | 요청·응답, 인증, 오류, 기존 계약 |
| 저장·조회·스키마 변경 | `docs/database.md` | 데이터 관계, 제약조건, 보관·삭제 정책 |
| 모듈 경계·외부 연동·배포 변경 | `docs/architecture.md` | 구성 요소와 책임, 통신 흐름 |
| 프로젝트 초기 구성·실행 설정 | `docs/getting-started.md`, `docs/architecture.md` | 도구 버전, 환경변수, 실행·검증 방법 |
| 기술 선택·장애 수정 | `docs/technical-decisions.md` | 기존 선택 근거와 확인된 문제 |
| 도메인 용어·아키텍처 결정 | `docs/agents/domain.md` | 용어집과 관련 ADR 읽기 규칙 |

## 2. 구현할 범위 정하기

작업을 시작할 때 관련 기능 ID, 포함 범위, 관찰 가능한 완료 조건과 검증 방법을
짧게 제시합니다. 전체 기획 기능은 개발 후보이며, 구현 권한이나 MVP 우선순위를
뜻하지 않습니다. 이번 요청 또는 이슈에 해당하는 범위만 구현합니다.

`미정`, `기획`, `미구현`은 상태 정보입니다. 이를 확정된 API·데이터 모델·제품
정책으로 취급하지 않습니다. 다음 기준으로 필요한 결정만 처리합니다.

- 기존 코드와 합의된 계약으로 정할 수 있는 구현 세부사항은 자율적으로 정합니다.
- 사용자 경험, 인증·권한, 데이터 보관·삭제, 외부 비용이나 공개 계약을 바꾸는
  미정 사항은 이번 작업에 영향을 줄 때 질문합니다. 이미 받은 답은 재사용합니다.
- 답이 필요한 부분을 분리하고, 답과 무관한 조사·설계·구현은 계속 진행합니다.
- 변경을 막지 않는 미정 사항은 그대로 남깁니다. 예를 들어 텍스트 입력 구현에
  음성 처리 기술이나 전체 분석 주기를 먼저 확정할 필요는 없습니다.

서비스 목표와 기획 기능은 해당 제품 문서를 기준으로 유지합니다. 특정 기능 요청을
전체 기획 기능의 일괄 구현 요청으로 확대하지 않습니다.

## 3. 계약을 구체화하고 구현하기

영향받는 명세의 해당 항목을 구현 전에 구체화합니다. 제안 단계인 내용은
`설계안`으로 표시하고, 확인된 내용과 구분합니다. 문서 양식 전체를 채우는 대신
이번 기능을 구현·검증하는 데 필요한 항목을 작성합니다.

- API: 메서드·경로, 입력과 제약조건, 성공·실패 응답, 필요한 인증·권한
- 데이터: 저장 대상, 관계·제약조건, 변경 시 마이그레이션과 기존 데이터 영향
- AI·음성 등 외부 연동: 입력·출력, 실패·지연 처리, 이번 작업의 책임 경계
- 말랑이·사운드: 클라이언트와 백엔드의 책임 및 API가 필요한 범위
- 초기 구성: 선택한 도구와 버전, 설정 주입 방식, 실행·테스트 명령

검증은 실제 저장소의 빌드 설정과 테스트 도구를 사용합니다. 변경된 동작의
핵심 성공 경로와 관련 실패 조건을 검증합니다. 외부 서비스에 의존하는 검증은
테스트 대역과 실제 연동 결과를 구분해서 보고합니다.

기술 선택의 근거와 확인된 문제 해결 과정은 `docs/technical-decisions.md`에
기록합니다. 용어집·ADR을 만들거나 변경할 때는 해당 도메인 문서 규칙을 따릅니다.

## 4. 완료 판정과 문서 동기화

다음 항목을 모두 확인한 뒤 완료를 보고합니다.

- 이번 작업의 완료 조건을 구현하고 검증했습니다. 남은 조건은 구체적으로 표시합니다.
- `docs/features.md`에서 해당 기능의 실제 구현 범위를 갱신했습니다. 기능 일부만
  구현했다면 전체 기능을 완료로 표시하지 않고 남은 범위를 함께 적습니다.
- API·스키마·아키텍처·실행 방법 중 변경된 계약을 해당 문서에 반영했습니다.
- 저장소 상태에 관한 문서 설명을 점검했습니다. 애플리케이션을 추가했다면
  README와 관련 문서의 ‘문서만 있음’, ‘미구현’ 등 설명도 실제 상태로 바꿉니다.
- 예제와 실제 동작의 일치, 문서 링크, `git diff --check`를 확인했습니다.
- 실행한 검사와 결과, 실행하지 못한 검사 및 이유를 구분했습니다.

문서 변경만 하는 작업은 해당 문서와 링크 검증으로 완료할 수 있습니다.
커밋·push·PR은 `docs/agents/workflow.md`와 `docs/agents/pr.md`를 따릅니다.
최종 보고에는 관련 기능 ID 또는 기반 작업 범위, 변경 내용, 실제 검증 결과,
PR 링크와 남은 제한을 포함합니다.

# PR 작성 규칙

## 제목과 범위

- 제목은 `docs/agents/workflow.md`의 커밋 형식인 `<type>(<scope>): <summary>`를 따른다.
  예: `feat(auth): 로그인 API 추가`. scope는 생략할 수 있다.
- 제목과 본문은 한국어로 작성하고, 코드 식별자는 원문을 유지한다.
- 하나의 PR에는 하나의 목적을 담는다. 리뷰어가 대화 기록 없이 이해할 수 있도록
  최종 변경 결과를 기준으로 작성한다.

## 본문 작성

`.github/pull_request_template.md`를 복사하고 안내 주석을 실제 내용으로 채운다.
템플릿의 제목을 유지하고, 해당 없는 항목에는 `해당 없음`과 필요한 이유를 적는다.

| 항목 | 작성할 내용 |
| --- | --- |
| Summary | 해결할 문제, 변경 후 동작, 주요 변경 내용 |
| Evidence | 변경 전후의 차이와 실제 실행한 검증 명령·결과 |
| Merge Danger | 되돌릴 수 있는지, 영향받는 API·데이터·설정, 필요한 배포·롤백 절차 |
| Related Issues | 완전히 해결하면 `Closes #123`, 일부 작업이면 `Refs #123`, 없으면 `없음` |

- Summary에는 변경을 설명하는 데 도움이 되는 작은 diff, 파일 트리 또는 흐름도를
  사용한다. 단순 변경은 짧은 설명으로 충분하다.
- Evidence에는 명령과 관찰한 결과를 적는다. 실행하지 않은 테스트를 통과했다고
  적지 않는다. 실행하지 못한 검증은 이유를 적는다.
- 문서 변경은 링크·내용·형식 검토 결과를 기록한다. 테스트 도구가 아직 없으면
  그 사실을 명시한다. Before/After는 테스트 로그 외에 설정이나 동작 차이로 설명해도 된다.
- Door는 쉽게 되돌릴 수 있으면 `two-way`, 데이터 삭제 등 되돌리기 어려우면
  `one-way`로 적는다. 기본값을 그대로 두기 전에 실제 변경을 확인한다.
- Blast Radius는 `auth API`, `repository docs`처럼 실제 영향 범위를 짧게 적는다.
  마이그레이션, 환경변수, API 호환성 변경이 있으면 구체적인 적용·복구 절차를 덧붙인다.
- 자격증명, 개인정보, 로컬 환경 파일의 내용을 본문이나 로그에 넣지 않는다.

## 게시와 수정

팀 저장소를 `origin`으로 사용한다. 작업 브랜치를 만든 뒤 그 브랜치를 `origin`에
푸시하고, 같은 저장소의 `main`을 대상으로 PR을 생성한다. `main` 직접 푸시는
금지한다. 훅을 우회하지 않으며, 게시 전에 원격 URL과 브랜치 추적을 확인한다.
리뷰와 CI 결과를 확인한 뒤 팀 절차에 따라 merge하고 로컬 `main`은 pull로 갱신한다.

1. 변경 diff와 검증 결과를 확인하고 실제 PR 본문을 파일로 작성한다.
   원격 저장소와 브랜치 선택은 `docs/agents/workflow.md`를 따른다.
2. `gh pr create`에는 `--body-file <본문 파일>`을 전달한다.
   CLI에서 본문을 명시할 때도 저장소 템플릿을 먼저 읽어 같은 구조로 작성한다.
3. 미완성 작업을 게시하는 경우 `--draft`를 사용한다.
4. 범위가 바뀌면 제목과 본문을 최종 구현에 맞게 수정한다.
   `gh pr edit <number> --repo <팀 저장소> --body-file <본문 파일>`을 사용한다.
5. 완료 후 PR 링크와 검증 결과, 남은 제한을 사용자에게 알린다.

이 파일은 작성 규칙이며 자동 검사 도구가 아니다. GitHub 웹에서 템플릿을
자동으로 표시하려면 대상 팀 저장소의 기본 브랜치에도 템플릿이 반영되어야 한다.
